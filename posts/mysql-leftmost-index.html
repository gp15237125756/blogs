从 B+ 树聊 MySQL 索引与最左前缀

与其背"最左前缀原则"，不如搞清楚联合索引在 B+ 树里是怎么排序的。理解了排序规则，索引失效的绝大多数情况都能自己推出来。

  • #MySQL
  • #数据库
  • #索引

联合索引在树里是怎么排的#

建立联合索引 idx_a_b_c (a, b, c) 时，MySQL 会先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序。

这一点直接决定了查询能否走索引：只有从最左列开始、连续匹配的等值条件，才能继续利用后面的列。

查询条件能用到索引的列说明
a = ?a正常
a = ? AND b = ?a, b正常
a = ? AND b > ? AND c = ?a, b范围查询后，c 用不上
b = ? AND c = ?无缺少最左列 a
a = ? AND c = ?a跳过了 b

注意第三行：b > ? 是范围查询，c 就断了。如果业务允许，把 c = ? 提到 b 前面，或者建立 (a, c, b) 的索引会更合适。

EXPLAIN 里真正要看的字段#

EXPLAIN SELECT id, a, b, c FROM t_order WHERE a = 1 AND b = 2 ORDER BY c;
+----+-------+------+---------------+---------+---------+-------------------+
| id | type  | key  | key_len       | ref     | rows    | Extra             |
+----+-------+------+---------------+---------+---------+-------------------+
|  1 | ref   | idx  | 8             | const   | 12      | Using index cond  |
+----+-------+------+---------------+---------+---------+-------------------+
  • type：至少要到 range，出现 ALL 基本说明没走索引
  • key：实际使用的索引，NULL 表示没用到
  • key_len：最直接判断"用了几列"的依据。可以反推用了几个索引列
  • Extra：Using index 是覆盖索引，Using filesort 表示排序没走索引，Using temporary 要警惕

key_len 的计算规则简单记成：不包含在 NULL 字段里的索引列会各占一份，varchar 还要加上长度标记字节。

索引失效的常见场景#

  1. 对索引列做运算：WHERE date(created_at) = '2026-06-21' 改写为 WHERE created_at >= '2026-06-21' AND created_at < '2026-06-22'
  2. 隐式类型转换：WHERE phone = 13800000000（phone 是 varchar）会全表扫描
  3. 前缀模糊匹配：LIKE '%abc' 用不上索引，LIKE 'abc%' 可以
  4. OR 连接非索引列：任一分支没索引，整体就退化
  5. 字符集不一致的联表：JOIN 字段字符集不同会触发隐式转换

覆盖索引与回表#

如果查询需要的列都在索引里，就不需要回表查主键：

-- 需要回表：索引里只有 a，b，还要取 c 之外的其他列
SELECT * FROM t_order WHERE a = 1 AND b = 2;

-- 覆盖索引：c 也在索引中，Extra 会显示 Using index
SELECT a, b, c FROM t_order WHERE a = 1 AND b = 2;

这也是为什么 SELECT * 在索引优化时经常碍事——它天然排除了覆盖索引的可能。

怎么选索引顺序#

一个可操作的判断顺序：

  1. 等值条件优先，范围条件放后面
  2. 区分度高的列优先（COUNT(DISTINCT col) / COUNT(*)）
  3. 考虑排序和分组，让 ORDER BY / GROUP BY 也能复用索引
  4. 控制索引数量，写多读少的表每个索引都是成本

索引不是越多越好。一个联合索引 (a, b) 已经能被 a = ? 复用，再单独建 (a) 就是冗余。

小结#

不要背"最左前缀"这四个字，而是记住：B+ 树是按索引列顺序逐级比较的，比较一旦不连续，后面的列就用不上。

把这条规则想清楚，EXPLAIN 的结果就不再需要猜了。
