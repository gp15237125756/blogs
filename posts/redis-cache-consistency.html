缓存与数据库一致性的四种方案

先删缓存还是先更新数据库？延迟双删到底能不能解决问题？把四种常见方案的失效场景摊开看，结论会清晰很多。

  • #Redis
  • #缓存
  • #分布式

问题本质#

缓存和数据库是两个存储，任何"先操作 A、再操作 B"的顺序都会有一个中间窗口，窗口内两者不一致。所以真正的问题不是"如何消除不一致"，而是把不一致窗口压到能接受的范围。

方案一：先更新数据库，再删除缓存#

也就是常说的 Cache Aside。绝大多数场景下这是默认选择。

并发下仍有极小概率出错：

T1: 读请求，缓存未命中
T2: 读请求，从 DB 读到旧值 v1
T1: 写请求，更新 DB 为 v2，删除缓存
T2: 把 v1 写入缓存        ← 缓存里留下了旧值

这个窗口出现的条件是"读请求恰好在写请求删缓存之后才写回缓存"，概率低但存在。缓解方式：

// 写回的缓存加一个较短的过期时间兜底
redis.set(key, value, 60, TimeUnit.SECONDS);

方案二：延迟双删#

更新数据库后，先删一次缓存，延迟几百毫秒再删一次。

public void update(Item item) {
    itemMapper.updateById(item);
    redis.delete(key(item.getId()));
    // 延迟删除，等待可能存在的旧值回填完成
    executor.schedule(() -> redis.delete(key(item.getId())), 500, TimeUnit.MILLISECONDS);
}

它的效果取决于延迟时间是否大于读请求的耗时，而这个耗时不可控。更稳妥的做法是让更新方在删缓存后等待所有在途读请求结束，但代价是复杂度上升。

结论：延迟双删可以缓解，不能根治。

方案三：先删除缓存，再更新数据库#

这个顺序的问题更大：

T1: 写请求，删除缓存
T2: 读请求，缓存未命中，从 DB 读到旧值 v1，写回缓存
T1: 更新 DB 为 v2                    ← 缓存里是 v1，DB 里是 v2

不一致窗口比方案一更长，所以不推荐。

方案四：订阅 Binlog 异步刷新#

用 Canal / Debezium 订阅数据库变更，异步删除或更新缓存。

优点：

  • 业务代码不感知缓存，解耦彻底
  • 缓存操作可以串行化，避免并发乱序

缺点：

  • 引入额外组件，链路更长
  • 存在秒级延迟，不适合强一致场景

这个方案适合缓存数据量大、业务代码难以统一改动的系统。

怎么选#

场景推荐方案
普通商品、用户资料先更新 DB 再删缓存 + 过期时间兜底
更新频率低、读取极频繁同上，但把过期时间拉长
缓存与 DB 需要强一致别用缓存，或改用分布式锁串行化
大量历史代码难以改造Binlog 异步刷新

两个容易忽略的细节#

缓存穿透：查询不存在的 key 会直接打到 DB。用空值缓存或布隆过滤器兜住。

// 空值也缓存，但过期时间要短
if (item == null) {
    redis.set(key, "NULL", 60, TimeUnit.SECONDS);
    return null;
}

热点 key 失效：大批 key 同时过期会造成 DB 尖峰。给过期时间加随机抖动：

int ttl = 300 + ThreadLocalRandom.current().nextInt(60);
redis.set(key, value, ttl, TimeUnit.SECONDS);

小结#

缓存一致性没有银弹。承认存在不一致窗口，然后用过期时间和兜底逻辑把影响控制住，比追求"绝对一致"更现实。

如果业务真的不能容忍任何不一致，那首先要质疑的应该是：这份数据真的需要放进缓存吗？
